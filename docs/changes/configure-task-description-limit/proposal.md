# Issue #3: проектный предел task.description

Статус: candidate classic/profiled/fix3.0.0 реализован на released Core0.13.90; локальная native-приёмка PASS, exact-source CI/PR завершаются.
Дата: 2026-11-10. Исходная база: пакеты v1.57.0. Реализация требует released Pri-Fly v0.13.90.
Источник: [уточнение владельца](https://github.com/StenHigh/prifly-aif-workflows/issues/3#issuecomment-6751418651).

Проект должен задавать предел `task.description` через поддерживаемую конфигурацию.
Настройка должна сохраняться при штатном обновлении workflow.
Без настройки остаётся прежний предел 12 000 символов.
Значение 32 000 служит примером проектного выбора, а не новым обязательным пределом.

## Проблема

Владелец сообщил об отказе `project questionnaire --prepare` на Core 0.13.88 и project profile `/5`.
Описание задачи содержит 16 557 символов, включая критерии и выдержки аудита.
Схема `aif:schema/task@1.1.0` допускает только 12 000 символов.
Core возвращает `schema_invalid` с указателем `/description`.
Сокращение описания теряет контекст; правка установленных схем мешает штатному обновлению.

На v0.13.89 `extend.yaml.settings` задаёт значения уже объявленных project-scoped inputs.
Project-scoped input — вход workflow с настройкой, общей для проекта.
Этот механизм не меняет `maxLength` схемы.
Отдельный вход с числом также не меняет контракт входа `task`.

## Объём

1. Найти поддержанный механизм проектного параметра, который формирует схему до проверки входа.
2. При нехватке механизма выделить связанную задачу Core с воспроизводимым примером.
3. Подключить параметр в classic и получить profiled штатной генерацией.
4. Согласовать контракт всех достижимых потребителей task внутри выбранного workflow.
5. Проверить сохранение настройки при обновлении пакета и неизменность существующих Run.
6. Обновить документацию, примеры, версии и проверки затронутых пакетов.

```text
Проектная настройка или default 12000
  -> проверка параметра
  -> сборка единого контракта task
  -> prepare: вход + контракт + сводка запуска
  -> reviewed start: тот же вход и контракт
  -> новый Run: сохранённый контракт -> все потребители task
```

Сборка здесь означает компиляцию пакета с проектной конфигурацией.
Сохранённый контракт включает точную ссылку на схему и её digest — контрольную сумму содержимого.
Поддержанный синтаксис: package `compile-parameters.yaml` и owner `project/compile-values.yaml`.
Параметр называется `task_description_limit`; [готовый пример](../../../examples/task-description-limit/README.md) содержит полные команды.

Native-пример на v0.13.89 подтвердил подстановку числа через авторский profile и `project compile --value`.
Штатные prepare/start не принимают `--value`; settings и наследование не меняют схему.
Авторский profile предлагает только заранее выпущенные значения.
Для проектного числового параметра остаётся граница Core; [результаты](native.md) описывают её точно.
Создана связанная [Pri-Fly #22](https://github.com/StenHigh/prifly/issues/22) с pinned reproducer и критериями C1–C8.
Core #22 закрыт и выпущен в v0.13.90. Candidate внедряет его механизм; [пакетная приёмка](acceptance.md) остаётся самостоятельной.

## Критерии приёмки

| ID | Требование |
|---|---|
| A1 | Проект задаёт положительное целое число без правки upstream-owned файлов. Штатное обновление сохраняет настройку и owner-файлы. |
| A2 | Без настройки граница остаётся 12 000: длина 12 000 проходит, 12 001 получает отказ. |
| A3 | При пределе 32 000 длины 16 557 и 32 000 проходят prepare/start. Длина 32 001 получает отказ до создания Run. |
| A4 | Нулевое, отрицательное, дробное, строковое, boolean и null значения получают точную диагностику настройки до запуска. Неподдерживаемое целое число также получает явный отказ. |
| A5 | Диагностика превышения называет `/description`, выбранный предел и фактическую длину. Кириллица и emoji считаются символами, а не байтами UTF-8. |
| A6 | Prepare и start используют один эффективный контракт. Эффективный контракт — схема после применения проектной настройки. Смена настройки после prepare требует новой сводки запуска. |
| A7 | Корень, вложенные workflow, step inputs и применимые проектные расширения согласованы по схеме task. Описание не обрезается на передаче. |
| A8 | Новый Run сохраняет эффективную схему и её точную идентичность. Изменение настройки не меняет состояние, входы или контракт существующего Run. |
| A9 | Continue сохраняет контракт исходного Run либо явно отказывает при несовместимой сборке до побочных эффектов. Он не подставляет текущий предел молча. |
| A10 | README, release guide, каталог и examples описывают поддержанный синтаксис, default, область действия, update и ограничения continue. |

В A7 нужны реальные classic/profiled маршруты, включая вложенные verify/review и повтор после repair.
Repair — исправление, после которого workflow повторяет проверку.
Приёмка должна подтвердить доступность полного task при планировании и всех его дальнейших передачах.
Если слой использует ссылку на артефакт, сравнить исходные байты по этой ссылке.
Подготовка запуска остаётся read-only: она не создаёт Run и не меняет рабочее дерево.

## Границы

Изменение относится к classic и производному profiled.
`aif-fix` получает тот же owned task1.2.0 и настройку; standalone сценарий входит в приёмку.
Старый внешний task1.1.0 остаётся frozen для прежних public consumers.
Project consumers переходят на schema_task; это требует major bump трёх пакетов до3.0.0.
Независимые схемы `aif-feature` и других пакетов не получают эту настройку автоматически.

Другие `maxLength`, число элементов, лимиты runtime и модели остаются самостоятельными контрактами.
Предел описания не обещает конкретное окно контекста модели.
Изменение не требует публикации, интеграции с tracker или миграции рабочей authority на этапе подготовки.
