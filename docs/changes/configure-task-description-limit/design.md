# Решение и границы

## Настройка до проверки task

Предпочтительное решение — объявленный пакетом типизированный параметр сборки.
Типизированный параметр принимает только значения указанного типа и диапазона.
Проект хранит выбранное значение в поддержанном owner-файле.
Owner-файл принадлежит проекту; обновление upstream-пакета сохраняет его.
Compiler применяет параметр до компиляции потребителей task и до валидации входного файла.

Параметр управляет только `task.description.maxLength` у объявленного пакетом контракта.
Default равен 12 000. Значение должно быть положительным целым числом.
Значение 32 000 должно поддерживаться.
Если Core требует верхнюю техническую границу, её нужно обосновать и документировать.
Настройка не должна разрешать произвольную подмену ID, digest или содержимого чужой схемы.

Выбор проектного синтаксиса ещё открыт. Здесь не вводится новое YAML-поле.
Native-проверка package profiles, project composition и `compile --value` завершена на v0.13.89.
Generic fixture — небольшой независимый пакет, который воспроизводит только нужный контракт.
Проверка подтвердила нехватку передачи произвольного значения в prepare/start; см. [результаты](native.md).
Пакетная реализация ждёт опубликованный и проверенный контракт такого механизма.

## Почему settings недостаточно

В released v0.13.89 функция `projectSetWorkflowSetting` записывает значение в `configuration.default` входа workflow.
Функция требует существующий вход с `configuration.scope: project`.
Она не изменяет определение схемы.
На classic вход `task` не является таким параметром; отдельного параметра длины нет.

Обычный runtime-вход с числом не поможет первичной проверке task.
Дополнительный gate после старта тоже не поможет: Core раньше проверяет предел 12 000.
Постоянное увеличение или удаление `maxLength` не даёт проекту выбрать свой предел.
Статические package profiles задаёт автор пакета; они не предоставляют произвольное целое число проекту.
Профили `fast/full/ultra` уже выбирают layout плана; настройка длины должна работать с каждым профилем.

Авторский profile `expanded` уже собирает согласованную схему 32 000 и пропускает полный task через child и worker.
Это поддержанный положительный контроль; конечные presets не дают проекту выбрать своё число.
`project compile --value` также подставляет число в source без profiles.
Но штатные prepare/start не принимают этот флаг и компилируют source заново без значения.
Даже import вручную собранного пакета не передаёт значение в эту повторную компиляцию.

Задача Core относится к проектной конфигурации compile values и их согласованной передаче в запуск.
Запрос не требует универсального schema override или нового механизма подстановки с нуля.
Он сохраняет вопрос о предпочтительном объявленном типизированном параметре и его области действия.

## Один контракт для всей сборки

Classic использует `contract_schema_task` в корне, plan и вложенных verify/review workflow.
Profiled копирует эти схемы штатным `tools/derive_profiled.py`.
`aif-fix` также поставляет `aif:schema/task@1.1.0` с теми же bytes.
Compiler должен согласовать все ссылки внутри выбранной сборки.
Изменение только корневого input недостаточно: дочерний input снова может отклонить длинное описание.

```text
Owner-параметр + package default
             |
             v
     эффективная схема task
             |
       +-----+----------+----------------+
       |                |                |
   root input       plan input     verify/review inputs
       |                |                |
       +---------- точные refs ----------+
                        |
                  snapshot нового Run
```

Snapshot — сохранённые определения и входы конкретного Run.
Разные проекты должны одновременно поддерживать разные пределы в одной authority.
Authority — хранилище определений и состояния Run.
Разные эффективные bytes не могут получать один и тот же неизменяемый ref.
Точное формирование compiled refs должен определять контракт Core.

Внешняя зависимость или project extension с фиксированной несовместимой схемой требует явного отказа сборки.
Нельзя скрывать такой конфликт до передачи task исполнителю.
Совместимое расширение получает ту же эффективную схему по поддержанному binding.
Binding — объявленная передача входа или выхода между компонентами.
Самостоятельный `aif-fix` требует отдельной квалификации, если реализация меняет его поставляемую схему.

## Prepare, start и continue

1. Compiler проверяет настройку и вычисляет эффективную схему.
2. Prepare проверяет полный task и показывает выбранный предел в сводке запуска.
3. Start проверяет digest просмотренной сводки и использует тот же контракт.
4. Core сохраняет точные определения и входной task в новом Run.
5. Следующие изменения настройки влияют на новые запуски.

```text
prepare(32000) -> review digest A -> start(A) -> Run с пределом 32000
                         |
                   настройка 40000
                         v
             start(A): отказ устаревшей сводки
             новый prepare -> digest B -> новый Run

исходный Run(32000) -> continue: исходный контракт или явный отказ совместимости
```

Continue не должен молча переключать схему исходного Run на текущее значение проекта.
Если released Core требует прежнюю сборку, документация должна дать проверенный способ её использовать.
Неподдерживаемое продолжение должно отказать до изменений дерева, claims и исходного Run.
Тест обязан сравнить состояние исходного Run до и после смены настройки.

## Пакеты и выпуск

В этой подготовке меняется только документация change, его реестр и `CONTEXT_STATE.md`.
Версии реализации выбираются по фактическому диффу после решения Core.
Изменение схемы требует согласованного bump схемы, зависимых steps/workflows и пакетов.
Profiled получается штатной генерацией; ручная правка его схемы не подходит.
Общий ID task требует проверки всех поставщиков, включая `aif-fix`.

Реализация должна обновить README classic/profiled, release guide, описание каталога и `examples/classic`.
Пример должен дать полный цикл установки, настройки, prepare/start и поддерживаемого continue.
Отдельно описать самостоятельный запуск и opt-in extensions с передачей task.
Обновление должно сохранить project settings и отказать при неразрешимом конфликте.
Все изменённые пакеты проходят действующие ворота на latest stable; generic fixture не заменяет их приёмку.
