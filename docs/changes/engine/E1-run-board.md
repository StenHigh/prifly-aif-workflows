## Проблема и ожидаемое поведение

При нескольких задачах существующий monitor даёт подробную диагностику Run,
но нужен компактный обзор: что выполняется, что ждёт ответа/ресурса, где
остановилась приёмка и какой Run продолжает предыдущую работу. Представить
это как дополнительный вид доски поверх сохранённого состояния Pri-Fly.

**E1 / приоритет P2.** База предложения: released Pri-Fly **0.13.76**.
Это новая проекция существующих Runs, не очередь задач и не новая машина состояний.
Желаемый вид вдохновлён [Software Factory](https://github.com/zazencodes/zazencodes-season-3/tree/555467c365e6750278efba09349369109f62f65f/src/software-factory-claude-code),
но не должен зависеть от Claude Code или названий AI Factory.

Пример: исходный Run закончился partial на недоступной проверке; continue
продолжает ту же работу и ждёт ответа. Пользователь видит актуальное ожидание,
ссылку на исходный partial и историю, а не две одинаково «застрявшие» карточки.
Связь определяется recorded resume/continuation provenance, не похожими title.

## Объём

- Дополнительный board view, сохраняющий текущую таблицу/детали monitor.
- Карточка: сохранённое название задачи и проекта, точный Run ID/workflow,
  текущая стадия/активные исполнения, состояние и причина ожидания/остановки.
- Категории — проекции runtime state: работа, ожидание ответа, ожидание ресурса,
  остановленное/неопределённое исполнение, terminal результат. Правила определить
  по существующим контрактам, не по догадкам из текста последнего лога.
- Для parallel отображать несколько активных стадий/ветвей; не выбирать одну
  «главную» по произвольному порядку.
- Recorded цепочка continue доступна из карточки; исходные outcomes и evidence
  не переписываются. Независимые Runs/ветки не сливаются по title.
- Из карточки открыть существующие graph, checks, artifacts, решения и журнал;
  сохранить проектные фильтры, поиск и позицию при возврате.

## Что уже существует / что не входит

В stable есть monitor, человекочитаемые title, граф и подробности исполнения,
resource ownership и решения. Не заказывать их заново и не дублировать
существующий change `make-monitor-list-human-readable`.

Нет hardcoded колонок plan/build/UX/merge, drag-and-drop изменения Run,
автоматического launch/continue, новой task identity или очереди. Информация о
переписке агентов, tool calls и метриках не выдумывается при отсутствии источника.
Новый сбор host telemetry и remote publication не входят в E1.

## Критерии приёмки

- [ ] **E1-A1:** Board отражает сохранённые runtime states и причины; неизвестное
  отображается явно. Колонки не создают новых terminal outcomes или verdicts.
- [ ] **E1-A2:** Generic workflows с разными именами стадий, без task title и
  без Git отображаются корректно; fallback помечен, AI Factory не зашит.
- [ ] **E1-A3:** Awaiting decision/resource и partial/failed/cancelled различаются;
  источник ожидания и требуемое действие доступны с переходом к деталям.
- [ ] **E1-A4:** Несколько active parallel branches видны одновременно. Pending/
  uncertain obligation не переименовывается в безопасно завершённую работу.
- [ ] **E1-A5:** Partial → continue → cancel → continue показывает актуальные
  Runs и записанную связь; original evidence сохраняется, независимые forks
  не объединяются эвристикой. Проверить повторный continue и legacy отсутствие связи.
- [ ] **E1-A6:** Проекты/authority не смешиваются; недоступный источник даёт
  локальную ошибку без исчезновения остальных карточек.
- [ ] **E1-A7:** Поиск, фильтры и navigation работают при большом наборе Runs;
  вид доски не возвращает общий лимит 200 и не требует загрузить все artifacts.
- [ ] **E1-A8:** Обновления не показывают mixed revision state; UI-тесты и
  живая browser-проверка подтверждают статусы, переходы, читабельность и возврат.
- [ ] **E1-A9:** Historical Runs/схемы сохраняют прежний смысл; если проекции
  нужны дополнительные fields, их источники и совместимость явно описаны.

## Зависимости и оформление change

Не зависит от новой task queue E2 или новых пакетов review. W1–W5 в
`StenHigh/prifly-aif-workflows` также не должны ждать эту UI-функцию.
Отдельное предложение очереди: [E2 / #5](https://github.com/StenHigh/prifly/issues/5).
При реализации оформить core change с deltas для local-run-monitor и, только
при необходимости, published read contracts; квалифицировать по фактическому
runtime state и живому UI, не только по строкам HTML.
