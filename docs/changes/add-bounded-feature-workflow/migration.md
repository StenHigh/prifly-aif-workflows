# W3 pilot / migration

Install aif-feature as a new folder and launch. Existing launches and extend
files keep their route; no automatic replacement or migration from classic,
profiled or aif-fix. Package starts at1.0.0; repository release/tag/catalog stays
at its last published version until a separate release instruction. W1/W2
components are self-contained copies, no prerequisite sibling installation.

Host must supply native aif-warmup, aif-plan, aif-implement, aif-commit,
aif-security-checklist, aif-review and separate plan TASK-FORMAT, implementation
LOGGING-GUIDE/IMPLEMENTATION-GUIDE and review SEVERITY references. Contract read
against2.19.0; actual installed skills are sealed at start, provenance is in
the new package inventory. No silent claim that source hashes attest arbitrary
installed/transformed copies.

Start with the backend JSON example, replace task/scope/criteria with actual
feature requirements and inspect exact task preview. For a UI feature choose
frontend, provide both required lenses/scenarios and a bounded owned environment
adapter following the W2 guide. Missing browser is a diagnostic, not a backend
profile. Baseline/provisioning commands belong to the project's declared effect
contract; no hidden dependency install or candidate reset.

Review plan_tests, constraints, retention and round limit. Prefer capture for a
disposable native working plan; retain keeps the reviewed owned tracked plan,
and the next feature will require explicit owner archival. Limit counts full
quality rounds, not repair writes; final failed round leaves unchanged evidence.

Continue a diagnostic partial or cancelled read-only quality via native prepare
and reviewed digest. Reconcile owned external environment before continuing a
cancelled product call. Forced writer cancellation is intentionally refused by
the released engine even after resolution: inspect/preserve its work and the E3
follow-up, rather than resetting the authority or silently recreating the Run.

Release checklist, when separately authorized: recheck latest stable Pri-Fly,
run required gates on that binary, assign repository release version, pin the
catalog to the reviewed exact release commit, test actual published add/update
and one complete published Run, then publish. Current draft catalog main is
not a release pin or a claim of published installation.
