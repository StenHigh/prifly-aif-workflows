# W1 — Явные доказательства выполненного ревью

Статус: **committed/pushed to main; CI PASS; accepted within recorded limits; unreleased**. Приоритет: **P1, первым**. Дата: 2026-10-14.
База: released Pri-Fly 0.13.76 / пакеты v1.51.2.

## Проблема и результат

Вердикт и список находок не показывают полноту приёмки. В исходном Factory
опубликованы PASS, при которых UI/UX readers не запускали требуемый браузер.
У нас `gate-result` содержит статус и findings, а `challenge-findings` —
доказательства отдельных находок; ни одно само по себе не описывает весь
объявленный состав выполненных и пропущенных проверок текущего candidate.

Добавить явный типизированный отчёт ревью. Обязательная невыполненная проверка
останавливает приёмку с причиной; optional-пропуск отображается как пропуск.
Один clean HEAD недостаточен для identity candidate: учитывается dirty дерево.

## Объём

- Схема отчёта, мосты и проверка полноты относительно объявленного состава.
- Основание проверки: code/diff, команда или браузер; выполненные проверки,
  результаты, пропуски и причины, evidence и привязка к candidate/раунду.
- Раздельные сведения о свежей сессии и фактически выбранной модели.
- Реализация поставляется отдельной папкой `aif-review-evidence`; первый
  потребитель — feature quality-контракт и fixtures W2/W3.
  По уточнению владельца 2026-10-14 `aif-classic` и производный `aif-profiled`
  сохраняются эталонными: их файлы, графы и shared schemas не меняются.
  Включение в существующий `aif-fix` также не входит в этот change.

## Зависимости и границы

Жёстких зависимостей на другие change нет. При baseline-проверке требуется
сохранность candidate по [#5](https://github.com/StenHigh/prifly-aif-workflows/issues/5).
Новый core API не предполагается. Не вводятся новые core verdicts, модельный
routing или утверждение о достоверности всех ответов LLM.

## Критерии приёмки

- **W1-A1:** Каждый объявленный check представлен ровно один раз: выполнен,
  недоступен, явно исключён или неприменим с основанием. Неизвестный/дублированный
  ID и отсутствующая обязательная запись не дают успешной приёмки.
- **W1-A2:** Требуемый browser-check без фактического browser evidence не
  принимается как browser-pass; отличать static review от browser review.
- **W1-A3:** Недоступная required dependency даёт diagnostic gate и partial,
  без repair/commit; выполненный check с дефектом маршрутизируется как дефект.
  Verdict пригодности отчёта не подменяет status проверки.
- **W1-A4:** Optional-пропуск обрабатывается объявленной политикой проекта,
  остаётся видимым и не переименовывается в выполненную проверку.
- **W1-A5:** HEAD, index, tracked/untracked bytes, удаления и modes входят в
  определённый candidate basis. Изменение candidate после отчёта инвалидирует
  его приёмку; изменение только файла evidence вне candidate не создаёт цикл.
- **W1-A6:** После repair и intervening edit нельзя принять evidence прошлого
  candidate; resume получает свежие checks для текущего дерева.
- **W1-A7:** Свежая сессия и другая модель не считаются одним свойством;
  unavailable/declined не обозначаются как подтверждённая независимость.
- **W1-A8:** Released CLI probes проходят положительный и отрицательные пути
  до finish; отдельно реальный host демонстрирует executed и unavailable checks.
- **W1-A9:** Проверены versioning и continue при изменении контракта: точный
  reusable prefix либо named refusal/replay point, без обещания silent migration.

Проверка identity и структуры не доказывает правдивость произвольного prose.
Evidence от команд по возможности собирается программой; browser observations
и модельные выводы сохраняют своё происхождение и границы проверки.
